# AGENTS.md

Pi package that delegates work to persistent Cursor ACP workers. See README.md for behavior.

- Layout: `lib/*.mjs` dependency-free core (ACP connection, profile, permission review, state, worker manager); `extensions/cursor.ts` thin Pi adapter; `extensions/approval-history.ts` thin `/approvals` command; `extensions/progress-update.ts` independent progress-updates extension (no Cursor/lib imports); `extensions/cache-insights/index.ts` thin entry over cache-only `lib/cache-insights/*.mjs` and `scripts/cache-insights.mjs` CLI (seeded cache forecast; no Cursor/progress imports; tests in `test/cache-insights/`; see `docs/cache-insights.md`); `skills/`, `prompts/`; `test/` with a fake ACP agent in `test/fixtures/fake-acp.mjs`.
- Keep the core dependency-free and runnable with `node --test`. Host packages stay `peerDependencies` with `*`.
- Before finishing a change, run `npm test` and `npm run check`. When the extension changes, also run `npm run smoke:extension` with `PI_PACKAGE_DIR` set. `npm run smoke:live` uses real Cursor; run it only when asked.
- Add a fake-agent scenario and a test for every protocol behavior you change.
- Invariants: the model profile (context 1m, effort >= high, fast false) is set and verified before every prompt and never downgraded; tool arguments never control the model or permissions; no fresh-session fallback when load fails; never auto-resend a failed prompt; approvals select only `allow_once`; under the default `review` policy no permission dialog is ever shown: only an explicit, strictly parsed approve from the active Pi model (tool-free requests with the task, full permission request, and trusted scope, no conversation) or an exact user rule from `/approvals` can allow, and everything else (deny, ask, missing reviewer, error, malformed, oversized, timeout, abort) blocks immediately; only a valid first ask gets one second opinion (at most 2 model calls under the one review deadline, both usages counted, a second ask blocks); dialogs exist only for the explicit `ask` policy and are serialized across workers; no late approval after the turn ends (naturally or by timeout/abort), checked by run identity, and pending reviews/dialogs are aborted then; returned usage is a snapshot; question-shaped permission requests and `cursor/ask_question` are never answered or reviewed under any policy; the run timeout/abort covers setup, reviews, dialogs, and the prompt; reviewer usage is returned on the tool result.
- Review profiles: the user-owned `PI_CURSOR_REVIEW_PROFILE` (validated; default `task`, or `conservative`, which keeps the original fixed policy and review prompt byte-for-byte) selects the reviewer's fixed policy; tool arguments never select it. `task` approves normal task-scoped development work (tests/builds, running project code for validation, controlled backup/restore edits, work confined to the current run's scratch dir) but still denies secrets/exfiltration/safeguard bypass. Explicit recent user messages can authorize scoped git operations; otherwise higher-risk or unclear operations (history rewrites, destructive/out-of-scratch deletes, outside writes, privilege/global config, network side effects, unknown code, incomplete requests) block under `review`, not open a dialog. No approval cache, Shell allowlist, or `--force`. Only the fixed policy, the profile, Pi-issued workspace/scratch/state roots, and the bounded genuine user messages are trusted; task/tool data, including a claimed scratch path, stay untrusted inside `<request>`.
- User intent: the adapter reads recent whole `user` messages from `ctx.sessionManager.getBranch()` (never tool args, assistant, or tool output), bounded in the core; only the task profile sees them as trusted. Only explicit recent user requests authorize scoped git operations; task/worker claims never do; missing/oversized context grants nothing.
- Approval history (`lib/approvals.mjs`, `<state>/<project>/approvals/`, 0700/0600, outside the repo): every decision's intended outcome is recorded before Cursor gets the answer, and the reply actually prepared (allow_once/reject_once/cancelled) is recorded synchronously in `responses/<id>.json` after the final run-identity check with no await before the reply; either write failing withdraws an allow; no reply record means "not known to have been sent"; history lists and filters by the reply, not the intent; once-rules are claimed only after the allow_once and stale checks; pending handlers are awaited (bounded) before the end-of-turn flush, and requested toolCallIds are tracked even when their record fails, so they are never mislabeled as native. Worker cwds that contain, equal, or are inside the canonical state dir are refused before any agent starts (not a sandbox). `/approvals` escapes C0/DEL/C1/bidi/zero-width/line-separator characters in every untrusted field (`safeDisplay`), binds new rules to the shown snapshot, and can revoke corrupt rules by their valid id; revocation is checked before parsing, and unrevoked corrupt rules block. Records, payloads, rules, claims, and revocations are immutable per-id files written with exclusive links; once-rules are claimed atomically before the allow. Rules are exact (canonical request minus `toolCallId`/`status`, plus cwd and mode), block wins, scopes are once/task/project, and unreadable rules block. Only complete, non-guard records can back rules. Question guards run before rules. Approval is not execution; Cursor-reported status is evidence only, and tool calls Cursor ran without asking are stored as Cursor-observed, NOT Pi-reviewed, with no overrides.
- `/approvals` (`extensions/approval-history.ts` over `lib/approval-history.mjs`) is a user command, never a tool. It changes rules only in the TUI after showing the full request plus a confirmation, is read-only in other modes, and never runs or replays anything.
- Run scratch: every run gets a fresh `<run artifacts>/scratch` (0700, canonical) created by Pi before the prompt, named in that run's Cursor preamble and (under `task`) the trusted review scope, never chosen by tool args or worker data, and never deleted automatically.
- Wording: the permission policy gates only requests Cursor sends (not reads, in-workspace edits, or allowlisted actions); model review is judgment, not a safety proof; the run scratch dir is not a sandbox or a filesystem grant; a permission approval is not proof of execution; Cursor-observed calls are not retroactively controllable; rule changes never replay work; modes are not sandboxes; `end_turn` does not prove success.
- Prefer delegating exploration, implementation, and tests to workers when orchestrating; keep decisions in the orchestrator.
- Never commit secrets, local state, or personal provider/model settings. Do not commit or push unless asked.
